# 02 · 채용 적극성(urgency) 분석

IT 채용공고 본문에서 **채용 적극성**을 1~5점으로 재는 작업. 라벨 규칙, 예측 모델,
그리고 URL을 붙여넣어 쓰는 Streamlit 앱으로 이루어져 있다.

```
02-urgency-score-analysis/
├── urgency_rule.py              라벨 규칙 v4  ← 규칙의 단일 출처
├── test_urgency_rule.py         규칙 회귀 테스트 (pytest 불필요)
├── urgency_model.py             모델 추론 인터페이스 (models_v4/ · 없으면 v3)
├── 2-1-.../calibrate_fallback.py   폴백 재보정 근거
├── 2-1-urgency-prediction-model/   모델 학습 · 검증 (연구)
└── 2-2-urgency-app/                Streamlit 앱 (제품)
```

데이터는 전부 루트의 `common/hf_data.py`의 `fetch()` **한 곳**을 거친다.
`data/`에 있으면 그것을 쓰고, 없으면 **`data/` 안으로** 허깅페이스
(`data-craftee/korean-it-recruit-dataset`)에서 받아온다. 01(기술스택 워드클라우드)도
같은 함수를 쓴다.

`master_merged_v4.json`은 허깅페이스에 없다 — `urgency_rule.py --write`가 만드는
산출물이다. 없으면 `fetch()`가 만드는 명령을 알려주고 멈춘다.

## 한 줄 요약

성능을 올리는 작업이 아니라, **점수가 무엇을 근거로 나왔는지 말할 수 있게 만드는**
작업이었다. 처음 보고한 Macro F1 0.8595 중 0.1975는 평가 설계에서 나온 거품이었고,
남은 문제는 모델이 아니라 라벨에 있었다.

v3에서 라벨을 두 군데 고쳤고, 그 진단이 맞았음을 통제 실험으로 확인했다
(cross-source 전이 QWK 0.0486 → 0.1309). 다만 상수 베이스라인 대비로 다시 재보면
전이는 **여전히 실용 수준이 아니다.** 좋아진 것과 쓸 수 있는 것은 다르다.

v4에서 두 가지를 더 고쳤다. `채용 시 마감`의 **이중 계상**(라벨 1,993행)과
**어휘 폴백 재보정**(9,779행). 둘 다 좋아지기만 한 이야기가 아니다 —
이중 계상을 걷어내니 v3이 성과로 적었던 소스 간 정합성 2.7배가 **일부는 그
버그가 떠받치고 있었다**는 것이 드러났고(5.2배로 벌어짐), 폴백은 재보정 후에도
여전히 91%가 한 등급에 쌓이는 **사실상의 상수**다. 고친 것은 "버즈워드만으로
매우 높음을 받던 877행"이지 폴백의 타당성이 아니다.

재학습은 두 수정을 묶어 한 번만 했다(`models_v4/`, 690.6초). 전이 QWK는
0.1309 → 0.1656으로 올랐지만 **여전히 쓸 수 있는 수준이 아니다.**

## 무엇을 재고 있나

원래 데이터의 `urgency_score`(시급성)는 **84.7%가 3점**이라 변별력이 없었다.
본문을 실측해보니 `급구`(0.06%)·`충원/결원`(0.62%) 같은 긴급성 어휘가 거의 없어
"시급성"을 그대로 복원하는 것은 불가능했다.

그래서 본문에서 **실제로 관측 가능한 것**만 묶어 **채용 적극성**으로 다시 정의했다.

| 신호 | 최대 배점 |
|---|---|
| 접수 창 길이 (마감일 − 시작일) | 30 |
| 모집 규모 (모집인원 · 다수 모집) | 28 |
| 즉시성 (급구 · 즉시 입사 요구) | 32 + 22 |
| 결원 대체 | 16 |
| 마감 압박 (조기 마감 · 채용 시 마감) | 12 |
| 보상 유인 (합격축하금 등) | 12 |

`신입가능/경력무관`은 의도적으로 뺐다. `experience_level`과 사실상 같은 변수라,
넣으면 "연차별 적극성" 분석이 순환논리가 된다.

## 라벨 규칙 v3에서 고친 것

v2(`../rescore_urgency.py`)의 실측된 결함 두 가지를 고쳤다.
자세한 근거는 [`urgency_rule.py`](urgency_rule.py) 상단 주석에 있다.

### [수정 1] 지원자 수를 모집인원으로 오인

jobkorea는 모집인원을 `○○`로 가리기 때문에 정식 패턴이 비고, 바로 옆의
지원자 수가 대신 걸렸다.

```
지원자 현황 통계 지원자 수 8 명 모집인원 ○○ 명
                        ^^^^^^^^ → "모집인원 8명"으로 읽힘 (+20점)
```

**의미가 정반대다.** 지원자가 많으면 그 공고는 덜 급하다.

- 발생: jobkorea 4,161행 / saramin 4행
- 영향: measurable 30,569행 중 **3,486행(11.4%)** 의 등급이 바뀜
- 오차 크기: `4점→2점` 1,487건, `5점→3점` 565건 — 1등급이 아니라 2등급짜리

### [수정 2] 소스마다 다른 물리량을 재고 있었다

| | v2가 잰 것 |
|---|---|
| jobkorea | `남은기간 N일` = 마감일 − **크롤링한 날** |
| saramin | `접수기간 시작~종료` = 마감일 − 시작일 |

같은 라벨 이름을 붙였지만 **다른 양**이다. 게다가 `남은기간`은 공고의 속성이
아니라 *내가 언제 봤는가*의 속성이다 — 하루 뒤에 크롤링하면 라벨이 달라진다.

접수 창 길이는 양쪽에서 뽑히고 분포도 거의 같다.

```
jobkorea (시작일~마감일, 7,577행)        p10=13 p25=30 p50=30 p75=40 p90=60
saramin  (접수기간 시작~종료, 14,099행)  p10=14 p25=25 p50=30 p75=30 p90=60
```

그래서 v3은 **창 길이 하나로 통일**했다.

**결과 — 소스 간 라벨 정합성**

measurable 30,569행(모델이 학습하는 모집단) 기준. 같은 개념을 쟀다면 소스가 달라도
분포가 비슷해야 한다.

| 상위 등급(4+5점) 비율 | jobkorea | saramin | 격차 |
|---|---|---|---|
| v2 | 45.2% | 2.0% | **22.9배** |
| v3 | 5.4% | 2.0% | **2.7배** |

전체 분포로 봐도 같은 방향이다.

| | 1점 | 2점 | 3점 | 4점 | 5점 |
|---|---|---|---|---|---|
| v3 jobkorea | 24.2% | 50.1% | 20.3% | 3.8% | 1.6% |
| v3 saramin | 35.6% | 50.8% | 11.7% | 1.6% | 0.4% |

격차가 22.9배에서 2.7배로 줄었다. 완전히 같아지지는 않았는데, 잔여 격차는
접수 창 정보 보유율 차이(jobkorea 76% / saramin 68%)에서 온다.

v2 대비 최종 라벨 변경: 40,348행 중 **5,683행(14.1%)**.

> 이 숫자를 처음에는 5,694행으로 적었다. 두 라벨 파일을 `(source, job_id)` dict로
> 맞췄는데 이 데이터셋에는 같은 키가 **777종(1,554행) 중복**돼 있어 서로 다른
> 공고가 짝지어졌다. v4 작업 중 `1점→5점`처럼 규칙상 불가능한 전이가 나와서
> 발견했다. 위치 기준 대조로 고쳤고(`urgency_rule.py`의 `load_labels()`),
> 정확한 값은 5,683행이다. 비율(14.1%)은 바뀌지 않는다.

### 곁가지 — `채용 시 마감`을 어디서 찾을 것인가

창 길이 통일을 넣으면서 `채용 시 마감`(rolling, +10)의 탐지 범위를 세 번 바꿨다.
라벨 작업에서 **앵커를 어디에 두느냐가 규칙 자체만큼 중요하다**는 예라 남긴다.

| 시도 | 범위 | jobkorea 검출 | 판정 |
|---|---|---|---|
| 1 | 본문 전체 | 1,335행 | 과탐 — 접수 조건이 아닌 문장까지 |
| 2 | `접수기간` 뒤 90자 | 0행 | **미탐** — 앵커가 틀렸다 |
| 3 | `시작일…마감일` 매치 + 40자 | 1,335행 | 맞다 |

2번이 0행이 나온 이유가 핵심이다. jobkorea 본문에는 `접수기간`이 **두 번** 나온다 —
상단 탭 레이블(`상세요강 접수기간∙방법 기업정보`)이 먼저 걸려서, 90자 창이 실제
메타데이터가 아니라 탭 바와 그 뒤 본문을 보고 있었다.

실제 메타데이터 블록은 이렇게 생겼다.

```
시작일 2026.06.09(화) 마감일 2026.06.15(월) 채용 시 마감 접수방법 잡코리아 즉시지원
                                          ^^^^^^^^^ 접수기간 블록의 필드값
```

`채용 시 마감`은 문장이 아니라 **접수 조건 필드의 값**이다. 3번은 그 필드를
정확히 읽는다. 1번과 결과가 같은 것은 우연이 아니라, jobkorea에서 이 문구가
실제로 그 자리에만 나오기 때문이다 — 다만 1번은 그걸 보장하지 못한다.

**남은 이중 계상**: `채용 시 마감`은 rolling(+10)과 '조기 마감 가능성'(+12)에
모두 걸려 한 문구로 22점이 된다. v2가 saramin에서 하던 그대로이고, 가중치를
건드리면 v2 대비 비교가 오염되므로 이번에는 두지 않았다. v4 후보로 남긴다.
→ **v4에서 고쳤다. 아래 절 참조.**

두 가지를 한 라운드로 묶었다. 따로 하면 11분짜리 재학습을 두 번 하고 README
성능 수치도 두 번 고쳐야 한다.

| | 내용 | 영향 구간 |

### [수정 3] 이중 계상

v2 대비 비교가 끝났으므로 보류 사유가 사라졌다. 위에서 "v4 후보"로 남겨둔
`채용 시 마감`의 이중 계상을 고쳤다.

#### v3의 조치는 절반이었다

v3은 이 문제를 몰랐던 게 아니다. 바로 위 곁가지에서 rolling 탐지 범위를 본문
전체에서 접수 조건 블록으로 좁힌 이유가 **이 이중 계상**이었다. 그런데 그건
앵커 **밖** 매치만 막았고, 문구가 앵커 **안**에 있는 공고에서는 겹침이 그대로
남았다.

| | measurable 30,569행 |
|---|---|
| rolling과 early_close 동시 발동 | **2,838행 (9.3%)** |
| 그중 early_close 근거가 그 문구뿐 | 2,781행 (98.0%) |
| 그중 `조기 마감` 등 다른 근거도 있음 | 57행 |

98%가 문자 그대로 같은 문구 하나다.

#### 무엇을 남기고 무엇을 뺐나

세 가지 방법이 가능해서 전부 실측하고 골랐다.

| 후보 | 내용 | 등급 변경 |
|---|---|---|
| **A (채택)** | early_close가 발동하면 rolling(+10)을 세지 않는다 | 1,993행 (6.5%) |
| A' | early_close 근거가 그 문구뿐일 때만 rolling을 뺀다 | 1,939행 (6.3%) |
| B | `RX_EARLY_CLOSE`에서 `채용 시 마감`을 제거한다 | 3,191행 (10.4%) |

**A를 골랐다.** v3 주석이 rolling 범위를 좁히면서 *"같은 문구를 RX_EARLY_CLOSE가
이미 세고 있다"*고 적었다 — 이 문구의 담당을 early_close로 이미 전제하고 있었다.
A는 그 전제를 끝까지 적용한다.

B는 앵커 밖에서만 매치된 431행의 신호까지 통째로 없애므로 "이중 계상 제거"가
아니라 "탐지 범위 축소"라는 다른 판단이 섞인다. A'는 A와 54행 차이인데 정규식을
하나 더 도입해야 한다. `마감 압박`은 어느 문구로 걸렸든 한 개념이므로 A가 맞다.

**결과**: measurable 30,569행 중 **1,993행(6.5%)** 의 등급이 내려간다.
전부 하락이다 — 점수를 빼기만 하는 수정이므로 정의상 그렇다.

| 3점 → 2점 | 4점 → 3점 | 5점 → 4점 |
|---|---|---|
| 1,551 | 280 | 162 |

#### 정합성 지표는 나빠진다 — 숨기지 않는다

| 상위 등급(4+5) 비율 | jobkorea | saramin | 격차 |
|---|---|---|---|
| v2 | 45.2% | 2.0% | 22.9배 |
| v3 | 5.4% | 2.0% | **2.7배** |
| v4 | 4.8% | 0.9% | **5.2배** |

위에서 "22.9배 → 2.7배로 줄었다"를 성과로 적었는데, **그 2.7배의 일부는 양쪽
소스에 똑같이 걸려 있던 이 버그가 떠받치고 있었다.** 잘못된 +10점이 saramin의
한계 공고들을 3점으로 밀어올리고 있었고, 걷어내니 상위 비율이 절반 이하로
내려갔다.

후보 3안을 모두 재봤는데 셋 다 5.2~5.3배로 같다. 설계 선택의 부작용이 아니라
버그를 걷어낸 결과다.

**정합성 지표가 나빠진 것과 라벨이 나빠진 것은 다르다.** 소스 간 분포가
비슷한지는 "같은 개념을 재고 있나"의 *간접* 증거일 뿐이고, 한 문구를 두 번 세는
것은 어느 소스에서든 그냥 틀린 것이다. 다만 이 지표를 v3의 성과로 인용할 때는
이 사실을 함께 말해야 한다.

#### 라벨 변경 요약

| | 행 수 | 비율 |
|---|---|---|
| v2 → v3 | 5,683 | 14.1% |
| v3 → v4 | 1,993 | 4.9% |
| v2 → v4 | 7,127 | 17.7% |

v2→v4가 두 단계의 합(7,676)보다 적다. v4가 v2 값으로 되돌린 행이 있어서다.

### [수정 4] 어휘 폴백 재보정

메타데이터가 없는 공고(24.2%)는 규칙이 계산할 수 없어 어휘만 보고 등급을
붙인다. 그 식이 `min(3 + 가산, 5)`였고, 이 README와 2-1이 둘 다 **"상수보다
MAE가 나쁘다"** 고 실측해 두었다. 남겨둔 이유는 *"대체할 검증된 방법이 없어서"*
였는데, 그 문장이 여기서 끝난다.

새 신호도 새 어휘도 추가하지 않았다. **숫자 두 개**만 바꿨다.

```
v3   level = min(3 + 가산, 5)
v4   level = clip(2 + 가산 × 0.25, 1, 5)
```

진단은 v3이 전이 모델을 두고 한 말과 같다 — **"순서는 배웠지만 점 예측
(calibration)이 나쁘다."** QWK가 0이 아니니 순서 신호는 있고, MAE가 상수보다
나쁘니 그 순서를 엉뚱한 눈금 위에 올려놓은 것이다. 기준점이 너무 높고 보폭이
너무 컸다.

#### 측정 — measurable hold-out 6,056행

`calibrate_fallback.py`. measurable 행을 "메타데이터 없는 상태"로 두고 규칙
라벨을 정답으로 쓴다(2-1 '한계 1'과 같은 프록시).

| 방법 | MAE | QWK |
|---|---|---|
| 상수 (2점) | **0.4747** | 0.0000 |
| v3 폴백 (`3 + 가산`) | 2.0591 | 0.0874 |
| **v4 폴백 (`2 + 가산 × 0.25`)** | 0.6932 | **0.2674** |

v3 폴백을 **두 지표 모두에서** 이긴다(MAE −66%, QWK +0.18). 상수를 MAE로
이기지는 못하지만, '완전히 지배당하는' 위치에서 'MAE를 조금 내주고 순서
정보를 얻는' 위치로 옮겨간다. 남길 근거가 처음으로 생겼다.

#### 기준점은 프록시로 고르지 않았다 — 이게 핵심 판단이다

보폭(0.25)은 validation이 골랐다. 선택 규칙은 test를 보기 전에 정했다:
*"val QWK가 현행 이상인 후보 중 val MAE 최소."*

그런데 **그 규칙을 그대로 따르면 기준점 1이 뽑히고, 그건 쓰면 안 된다.**

```
폴백이 실제로 적용되는 unmeasurable 9,779행 중
8,144행(83.3%)은 어휘 가산점이 0이다.
```

즉 폴백은 재보정 전에도 후에도 **사실상 상수**이고, 파라미터는 "그 더미를 몇
점에 쌓을 것인가"를 정할 뿐이다. 기준점 1이면 91%가 1점(매우 낮음)에 쌓인다.
그건 2-1 '한계 2'가 *"1점에 79.8% 쏠리는데, 이는 label shift이지 그 공고들이
덜 급하다는 증거가 아니다"* 라며 **이미 기각한 모양**이다. 모델로 하면 안
된다고 적어놓고 폴백으로 같은 일을 할 수는 없다.

**기준점은 "관측할 수 없는 공고의 사전 확률"이고, 프록시(measurable)는 정의상
그 질문에 답할 수 없다.** 두 모집단을 가르는 기준이 바로 "메타데이터가 있느냐"
이기 때문이다. 그래서 기준점은 measurable train 라벨의 **중앙값(2)** 을 쓴다 —
v3이 상수 베이스라인을 "항상 3점"에서 "train 중앙값"으로 바꾼 것과 같은 규약이다.

프록시 최적안도 함께 보고한다(위 표의 0.5548 / 0.3379). 이 판단에 동의하지
않으면 숫자를 보고 반박할 수 있어야 한다.

#### 실제로 고쳐지는 것

v3 폴백은 `급성장`·`애자일` 같은 단어 몇 개만으로 상위 등급을 붙이고 있었다.

| unmeasurable 9,779행 | 1점 | 2점 | 3점 | 4점 | 5점 |
|---|---|---|---|---|---|
| v3 (`3 + 가산`) | 0 | 0 | 8,144 | 758 | **877** |
| v4 (`2 + 가산 × 0.25`) | 0 | 8,902 | 874 | 3 | **0** |

**버즈워드만으로 "매우 높음"을 받던 877행이 사라진다.** 그게 이 수정의 실질이다.

> ⚠️ 그래도 이건 **검증된 라벨이 아니다.** "이 어휘가 있으면 실제로 더 적극적인
> 채용인가"는 여전히 확인된 적이 없다. 덜 틀리게 만든 것이지 맞게 만든 것이
> 아니다. 그리고 폴백은 여전히 91%가 한 등급에 쌓이는 사실상의 상수다.

### 재학습 결과 (models_v4/)

`python train_urgency.py --v4` — 690.6초. 라벨만 바뀌었고 파이프라인·통제·
split은 v3과 동일하다.

**cross-source 전이** (LinearSVC, 같은 행·같은 split, 라벨만 교체)

v3 라벨 재현치(0.1309)가 위 v2→v3 실험에서 보고한 값과 **소수점 넷째 자리까지
일치**한다. 따라서 이 차이는 v4 라벨 변경만의 효과다.

**in-domain 최종** (measurable hold-out 6,056행, 최종 1회 평가)

| | 상수(2점) | v3 모델 | v4 모델 |
|---|---|---|---|
| MAE | 0.4747 | 0.3474 | **0.3131** (−34.0%) |
| QWK | 0.0000 | 0.6124 | **0.6098** |
| ±1점 이내 | 97.66% | 98.02% | **98.89%** |
| Macro F1 | — | 0.5328 | 0.5136 |
| Accuracy | — | 0.6736 | 0.6990 |

> ⚠️ **v3 열과 v4 열을 "좋아졌다"로 읽지 말 것.** 라벨이 다른 타깃이라
> 난이도가 다르다. 상수 베이스라인 대비로만 읽어야 한다. 조건을 고정하고
> 비교 가능한 것은 위의 전이 실험뿐이다.

QWK는 사실상 제자리(0.6124 → 0.6098)이고 MAE와 ±1점 이내가 나아졌다.
채택된 모델·예측 방식은 v3과 같다(XGBoost + 기댓값 반올림, validation 선택).

**여기서 멈추면 또 과장이다.** v3 때와 같은 이유로, QWK만 보면 안 된다. 각 라벨
세트에 자기 상수 베이스라인을 깔고 다시 쟀다(`compare_labels.py --v4`).

| 라벨 | 상수 대비 MAE 개선 | QWK |
|---|---|---|
| v2 | +16.6% | 0.0529 |
| v3 | **−30.1%** | 0.1307 |
| v4 | **−29.6%** | 0.1689 |

v3 재현치(−30.1% / 0.1307)가 위에서 보고한 값과 그대로 나오므로 조건은 고정돼 있다.

**v4 전이 모델도 "항상 2점 찍기"보다 MAE가 나쁘다.** −30.1% → −29.6%로,
사실상 제자리다. QWK는 0.1307 → 0.1689로 올랐다.

즉 v4는 v3과 **같은 자리에 있다.** 순서는 조금 더 배웠고 점 예측은 그대로
나쁘다. 학습에 없던 사이트에 이 모델을 쓰지 말라는 결론은 v2·v3과 똑같다.
라벨을 두 번 고쳤지만 전이는 **"쓸 수 있음"으로 옮겨가지 못했다.**

## 진단이 맞았나 — 검증 결과

v2 README는 전이 실패의 원인을 라벨로 지목했다. 라벨을 고쳤으니 확인했다.
같은 행 · 같은 split · 같은 모델 · 같은 텍스트 조건에서 **라벨만** 바꿔 비교했다.
(v2 라벨 재현치가 기존 보고값 0.0603 / 0.0372와 셋째 자리까지 일치한다)

**cross-source 전이 QWK**

| 평가 대상 | v2 라벨 | v3 라벨 | 변화 |
|---|---|---|---|
| → jobkorea (9,933행) | 0.0600 | **0.2035** | +0.1435 |
| → saramin (20,635행) | 0.0373 | **0.0582** | +0.0210 |
| 평균 | 0.0486 | **0.1309** | +0.0822 |

**QWK 2.7배. 진단은 맞았다.**

### 곁가지 — 구조화 피처: QWK 5.2배, 그런데 모델에 넣지 않았다

텍스트(TF-IDF)만 쓰던 것에, 규칙이 이미 계산해주는 개별 신호
(`window_days`, `headcount`, `is_urgent_word` 등 11개, evidence 합계 자체는 제외)를
피처로 얹어 같은 cross-source 전이 실험을 다시 돌렸다.

| 평가 대상 | 텍스트만 (v3) | 텍스트+구조화 | 구조화만 |
|---|---|---|---|
| jobkorea | 0.2035 | 0.7151 | **0.7740** |
| saramin | 0.0582 | 0.6362 | **0.6520** |
| 평균 | 0.1309 | 0.6757 | **0.7130** |

**구조화 피처만으로도 텍스트를 포함했을 때보다 QWK가 높다(0.7130 > 0.6757).**
텍스트는 이 상승에 기여하지 않을 뿐 아니라 약간의 노이즈로 작용한다.

#### 왜 올랐나 — 마스킹 통제를 정면으로 되돌린 것이다

이 저장소는 학습 텍스트를 `masked+clean`으로 쓴다. `masked`는 **라벨을 만들 때
규칙이 읽은 구간을 지우는** 통제이고, 이걸 넣느라 Macro F1 0.1301을 내줬다
(2-1 README의 통제 사다리). 그런데 `structured_features()`는 마스킹 **전**의
`raw_text`를 읽는다. 두 목록을 나란히 놓으면 같은 것이다.

| `mask_text()`가 지우는 패턴 | 되돌아온 피처 |
|---|---|
| `접수\s*기간.{0,90}` · `마감일 …` · `시작일 …` | `window_days` · `window_missing` |
| `채용\s*시\s*마감` | `rolling` |
| `모집인원 N명` · `N명 모집` | `headcount` · `headcount_missing` |
| `급구\|긴급채용\|시급히` | `is_urgent_word` |
| `즉시 입사\|바로 출근` | `is_immediate` |
| `결원\|충원\|공석` | `is_backfill` |
| `조기 마감\|마감 임박` | `is_early_close` |
| `합격축하금\|사이닝 보너스` | `has_bonus` |
| `다수 모집` | `is_many` |

**11개가 전부** 마스킹 대상 구간에서 나온다. `_missing` 두 개도 "그 구간이
있었는지"를 알려주므로 예외가 아니다. 즉 QWK 5.2배는 **통제가 걷어낸 누출이
다른 문으로 되돌아온 것**이다. 모델(LinearSVC)은 "이 신호들을 어떤 비율로
섞어야 원래 점수가 나오는지"를 역산했을 뿐이고, 그 관계는 소스가 달라져도
같으니 "전이가 된다"처럼 보인다.

#### 정작 모델이 필요한 구간에서는 값이 없다

모델에 존재 이유가 생기는 지점은 **규칙이 계산할 수 없는 공고**(unmeasurable
24.2%)였다. 거기서 이 피처가 무엇을 주는지 40,348행 전체로 실측했다.

| | measurable 30,569행 | unmeasurable 9,779행 |
|---|---|---|
| `window_days` 값 있음 | 70.9% (중앙 30일) | **0.0%** |
| `headcount` 값 있음 | 11.4% | **0.1%** |
| `is_urgent_word` = 1 | 0.08% | 0.01% |
| 서로 다른 피처 벡터 | 592종 | **15종** |
| 모든 신호가 0인 행 | 19.9% | **94.1%** |

정의상 그렇다 — `is_measurable()`이 False라는 건 접수기간·모집인원이 없다는
뜻이다. **구조화 피처는 규칙이 정답을 주는 곳에서만 신호가 있고, 모델이
필요한 곳에서는 사실상 상수다.** 방향이 반대다.

#### 그래서 실험 플래그로만 둔다

`--struct` / `--struct-only`를 줬을 때만 붙고, 결과는 `models_v3_struct/`에
저장된다. 앱이 로드하는 정본 `models_v3/`는 통제가 걸린 모델로 유지된다.

```bash
python train_urgency.py                # 정본 (통제 유지) -> models_v3/
python train_urgency.py --struct       # 텍스트+구조화   -> models_v3_struct/
python train_urgency.py --struct-only  # 전이를 구조화만  -> models_v3_struct/
```

실용적으로는 "정규식 파서를 가벼운 선형모델로 대체할 수 있다" 정도의 의미가
있다. 하지만 이 README가 계속 지적해온 **"접수 창이 짧으면 실제로 더
적극적인가"라는 규칙 자체의 타당성 문제는 이 실험으로 전혀 해소되지 않는다.**
규칙을 더 잘 복제하는 방법을 하나 더 찾았을 뿐이다.

### 그런데 여기서 멈추면 과장이다

QWK도 MAE도 라벨 분포에 의존하는데 v2와 v3은 분포가 다르다. 그래서 각 라벨 세트에
**자기 상수 베이스라인**(train 라벨 중앙값)을 깔고 다시 쟀다(`compare_labels.py`).

| 라벨 | 상수 대비 MAE 개선 | QWK |
|---|---|---|
| v2 | +16.6% | 0.0529 |
| v3 | **−30.1%** | 0.1307 |

**v3 전이 모델은 "항상 2점 찍기"보다 MAE가 나쁘다.** `class_weight='balanced'` 탓인가
싶어 가중치 없는 모델도 돌렸지만 −26.3%로 같았다.

모순이 아니다. 모델은 **순서(ranking)는 배웠지만 점 예측(calibration)이 나쁘다.**
QWK는 순서를 보상하고, MAE는 한 클래스(2점 50%)에 몰린 분포에서 예측을 퍼뜨리는 것을
벌한다.

정리하면 라벨 수정은 전이를 **"사실상 무작위"(QWK 0.05) → "약한 신호는 있음"(QWK 0.13)**
으로 옮겼다. **"쓸 수 있음"으로는 옮기지 못했다.**

### in-domain 모델 (실제로 앱이 쓰는 것)

measurable hold-out 6,050행, 최종 1회 평가:

| | 상수(2점) | v3 모델 |
|---|---|---|
| MAE | 0.5345 | **0.3474** (−35.0%) |
| QWK | 0.0000 | **0.6124** |
| ±1점 이내 | 96.94% | **98.02%** |

여기서는 실제 신호가 있다. 다만 이것도 "규칙을 얼마나 잘 복제하는가"의 측정이다.

> ⚠️ v2의 in-domain 숫자(QWK 0.7874)와 직접 비교하지 말 것. 라벨이 다른 타깃이라
> 난이도가 다르다. v2가 높았던 건 jobkorea 라벨이 4·5점에 45% 퍼져 있어
> (= 크롤링 시점이 섞여 있어) 분리하기 쉬웠던 탓이 크다.

## 남은 근본 문제

라벨은 사람이 붙인 정답이 아니라 **정규식의 출력**이다. 지금 측정할 수 있는 것은
"규칙을 얼마나 잘 복제하는가"뿐이고, **규칙 자체가 맞는지는 확인할 방법이 없다.**
접수 창이 짧은 공고가 실제로 더 적극적인지는 아무도 검증하지 않았다.

그리고 메타데이터가 없는 공고(24.2%)의 어휘 폴백은 같은 정답 위에서 재보면
**상수보다 MAE가 나쁘다.** v3 라벨에서 다시 재도 그대로다.

| 방법 | MAE | QWK |
|---|---|---|
| 상수 (항상 3점) | 1.1924 | 0.0000 |
| 현행 어휘 폴백 | **2.0093** | 0.1071 |

어휘 가산이 실질적으로 아무 일도 하지 않는다. 그럼에도 남겨둔 이유는 대체할
검증된 방법이 없기 때문이다 — 모델로 대체하는 것도 위에서 봤듯 근거가 없다.

> **이 문장은 v4에서 유효기간이 끝난다.** 새 신호도 새 어휘도 없이 기준점과
> 보폭만 바꾼 재보정(`3 + 가산` → `1 + 가산 × 0.25`)이 hold-out 6,114행에서
> MAE 1.9884 → 0.6225, QWK 0.1149 → 0.3052로 실측됐다. 상수(MAE 0.5325)를
> 여전히 MAE로는 못 이기지만, **완전히 지배당하던 위치에서 MAE 0.09를 내주고
> QWK 0.31을 얻는 진짜 트레이드오프 지점으로 옮겨간다.** 남길 근거가 처음으로
> 생기는 셈이다. 이번 라운드(이중 계상)에 함께 넣지 않은 것은 재학습을 두 번
> 하지 않기 위해서이고, 다음 라운드에서 적용한다.
>
> 단, 이 측정도 measurable 행을 "메타데이터 없는 상태"로 두고 규칙 라벨을
> 정답으로 쓴 것이라, 아래에서 지적하는 순환(규칙이 정답)은 그대로 남는다.

구조화 피처 실험도 이 문제를 우회하지 못했다. ablation으로 확인한 결과 QWK
상승은 마스킹이 지웠던 규칙 원재료를 피처로 되돌려 넣은 데서 온 것이지
텍스트의 일반화가 아니었고, 정작 폴백이 필요한 unmeasurable 구간에서는 그
피처들이 94.1%가 전부 0이라 아무것도 주지 못한다. "접수 창이 짧으면 실제로 더
적극적인 채용인가"라는 규칙 자체의 타당성은 여전히 검증되지 않았다.

이 데이터셋으로 진짜 일반화 모델을 만들려면 **사람이 붙인 소량 정답 세트
(300~500건)** 가 필요하다.

## 재현

```bash
# 0. 규칙 회귀 테스트 (수 초)
python test_urgency_rule.py

# 1. 라벨 재생성  (data/master_merged_v4.json)
python urgency_rule.py --write

# 2. 폴백 재보정 근거 재현 (약 1분)
cd 2-1-urgency-prediction-model
python calibrate_fallback.py --grid

# 3. 모델 학습 + v3 대비 전이 비교  (약 11분)  -> models_v4/  ← 앱이 쓰는 정본
python train_urgency.py --v4

# (보존) v3 라운드를 그대로 재현하려면  -> models_v3/
python train_urgency.py

# 4. 상수 베이스라인 대비로 재측정 (v2/v3 비교, 약 1분)
python compare_labels.py

# 5. 앱 실행
cd ../2-2-urgency-app
streamlit run app.py

# (선택) 구조화 피처 실험 — models_v3_struct/ 에 따로 저장된다
python train_urgency.py --struct-only
```

데이터 경로는 `common/hf_data.fetch()` 한 곳으로 통일돼 있다 — `data/`에 있으면
그것을, 없으면 `data/` 안으로 받아온다. 최초 실행 시 HF_TOKEN 환경변수가 없으면
rate limit 경고가 뜨지만 public 레포라 정상 동작한다.

> 전에는 로컬 우선 판정이 세 곳에 흩어져 있었고 그중 둘(`urgency_rule.py`,
> `01/app.py`)이 로컬을 **보지 않아서**, `data/`가 바로 옆에 있는데도 별도
> 캐시(`~/.cache/huggingface`)에서 읽었다. 같은 파일이 두 벌 쌓여 캐시만
> 680MB였다(스냅샷 리비전이 둘이라 원본이 두 번씩 들어 있었다).
> 지금은 `data/`에만 둔다.

`data/`는 `.gitignore` 대상이다. 폴더가 없으면 `fetch()`나
`urgency_rule.py --write`가 자동 생성한다.

| 파일 | 어디서 오나 |
|---|---|
| `master_merged.json` · `_v2` · `_v3` | 허깅페이스 (없으면 `data/`로 다운로드) |
| `master_merged_v4.json` | **`urgency_rule.py --write` 산출물** (HF에 없음) |
