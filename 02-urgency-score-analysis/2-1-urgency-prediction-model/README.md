# 채용 적극성(urgency) 예측 모델

IT 채용공고 본문에서 **채용 적극성**(마감 임박도·모집 규모·즉시 입사 요구 등을 묶은 1~5점 지표)을 예측하는 모델.

처음 만든 모델은 Macro F1 0.8595를 기록했지만, 검증 설계를 뜯어보니 그 점수의 상당 부분이 거품이었다. 이 문서는 **거품을 걷어내는 과정과, 걷어낸 뒤 남은 것**을 기록한다. 최종 모델은 성능이 아니라 **적용 범위가 명확한 것**을 목표로 했다.

---

## 최종 모델

| 항목 | 값 |
|---|---|
| 알고리즘 | XGBoost (`multi:softmax`, early stopping @ 256/400) |
| 피처 | TF-IDF 1~2gram, 30,000 |
| 텍스트 조건 | `masked+clean` (라벨 산출 구간 제거 + 사이트 템플릿 제거) |
| 학습 데이터 | measurable 공고 19,428행 (val 4,863 / test 6,106) |
| 예측 방식 | 클래스 확률의 **기댓값 반올림** |
| 파일 | `models_transfer/transfer_model.joblib` |

### 성능 (measurable hold-out 6,106행)

| 지표 | 값 |
|---|---|
| **QWK** (주 지표) | **0.7874** |
| **MAE** | **0.4291** |
| 인접 오차 내 정확도 (±1점) | **96.4%** |
| Macro F1 | 0.5563 |
| Accuracy | 0.6097 |

라벨이 1~5 순서형이므로 QWK와 MAE를 주 지표로 삼았다. "1점을 5점으로" 틀린 것과 "3점을 4점으로" 틀린 것은 같은 오류가 아니다. **예측의 96.4%가 실제 값의 ±1점 안에 들어온다.**

### 적용 범위 — 반드시 지킬 것

**✅ 쓸 수 있는 곳**: 본문에 마감일·접수기간·모집인원 같은 채용 메타데이터가 있는 공고 (`rescore_urgency.is_measurable()`이 True)

**❌ 쓰면 안 되는 곳**:
- 메타데이터가 없는 공고 (전체의 24.2%) — 아래 "한계" 참조
- 학습에 없던 채용 사이트 — cross-source 전이가 실패한다 (QWK 0.04)

> **먼저 규칙을 고려할 것.** 메타데이터가 있는 공고라면 `rescore_urgency.py`를
> 그대로 돌리는 편이 낫다. 라벨 자체가 그 규칙의 출력이므로 규칙은 정의상 정답을 주고,
> `urgency_reason`으로 근거 문장까지 나온다. 이 모델은 그 규칙의 근사치이며,
> 규칙을 쓸 수 없는 상황의 참고값과 연구 재현이 용도다.

### 사용법

`.joblib`을 직접 로드하면 안 된다. `predict()`가 argmax를 돌려주므로 위 성능이
재현되지 않는다. 최종 예측 방식(기댓값 반올림)과 전처리(`masked+clean`)를 함께
묶어둔 `predict_urgency.py`를 쓴다.

```python
from predict_urgency import UrgencyPredictor

p = UrgencyPredictor()
p.predict(["공고 본문 ...", "..."], ["saramin", "jobkorea"])
# array([2, 4])   1~5점

p.predict_with_scope(texts, sources)
#    urgency_score  in_scope
# 0              2      True     <- 검증된 범위
# 1              4     False     <- 근거 없음. 참고값으로만 쓸 것
```

`in_scope=False`는 그 공고에 메타데이터가 없어 모델이 검증되지 않은 영역이라는
뜻이다. 이 플래그를 무시하지 말 것.

```bash
python predict_urgency.py    # 자기검증: 저장된 최종 성능이 재현되는지 확인
```

## 어떻게 여기까지 왔나

라벨 `urgency_score`는 `rescore_urgency.py`가 본문에서 정규식으로 만든 **결정론적 값**이다. 즉 `라벨 = f(raw_text)`이고, 그 `f`가 읽은 구간이 학습 피처에 그대로 들어 있었다. 이 상태의 높은 점수는 "시급성을 예측했다"가 아니라 **"정규식을 역공학했다"** 에 가깝다.

통제를 하나씩 넣으면서 점수가 어떻게 움직였는지:

| 단계 | Macro F1 | 무엇이 빠졌나 |
|---|---|---|
| v1 (중복 미제거 · 랜덤 split) | 0.8595 | — |
| + 중복 공고 그룹 분리 | 0.8459 | −0.0136 · 같은 공고를 train/test 양쪽에서 본 것 |
| + 라벨 산출 구간 마스킹 | 0.7158 | −0.1301 · 정규식 역공학 |
| + 사이트 템플릿 제거 | 0.6620 | −0.0538 · 사이트 지문 |

**보고했던 0.8595 중 0.1975가 평가 설계에서 나온 거품이었다.**

각 통제의 근거:

**중복** — 정규화 후 전문 일치 공고가 6.97%, 앞 600자 일치가 11.2%였다. 라벨이 텍스트의 결정론적 함수라 이 중복이 train/test에 갈리면 암기로 정답을 맞힌다. `StratifiedGroupKFold`로 근사중복을 한 덩어리로 묶었다.

**라벨 누출** — 라벨 산출에 쓰인 구간(`남은기간 N일`, `접수기간`, `모집인원 N명`, 긴급 어휘)을 마스킹하고 다시 학습해 누출 규모를 쟀다. 모델이 강할수록 누출 의존도가 컸다: LinearSVC 7.3%, LogReg 6.8%, XGBoost 10.0%.

**사이트 템플릿** — v1의 중요 피처 TOP 20이 `등록일`·`기업정보`·`잡코리아 이력서`·`지원방법`처럼 전부 사이트 템플릿이었다. 특히 **jobkorea 본문의 72%가 꼬리(추천공고 목록 = 다른 공고의 내용)** 였다. `max_df=0.9`로는 안 걸러진다 — 전체 코퍼스 기준이라 jobkorea 저작권 고지의 전체 DF는 0.247에 불과하다. 소스 *내부* DF를 봐야 잡힌다.

**베이스라인** — v1에는 비교 기준이 없었다. Dummy → source-only → LinearSVC → XGBoost 사다리를 놓으니 LinearSVC가 3초에 XGBoost(32분)의 대부분을 따라잡았다. 이후 모든 실험은 선형으로 먼저 스크리닝했다.

### 과제 재정의

거품을 걷고 나니 더 큰 문제가 보였다. **라벨이 규칙의 출력이라면, 규칙을 그냥 돌리면 되지 모델이 왜 필요한가?**

모델에 존재 이유가 생기는 지점은 하나였다 — **규칙이 계산할 수 없는 공고**.

| | 행 수 | 라벨의 성격 |
|---|---|---|
| measurable | 30,569 (75.8%) | 메타데이터를 읽고 만든 **검증된 라벨** |
| unmeasurable | 9,779 (24.2%) | 메타데이터가 없어 3점에서 어휘 가산만 한 **미검증 폴백** |

그래서 **measurable로만 학습**하도록 바꿨다. 텍스트를 `masked+clean`으로 둔 이유도 달라진다 — 정직한 평가 때문이 아니라, 적용 대상에 마감일 구간도 템플릿도 없으므로 **학습 텍스트의 도메인을 맞추기 위해서**다.

## 부딪힌 한계

### 1. 현행 어휘 폴백은 실제로 근거가 없다 (확인됨)

measurable hold-out을 "메타데이터 없는 상태"로 두고, 같은 정답 위에서 두 방법을 비교했다.

| 방법 | QWK | MAE |
|---|---|---|
| 상수 baseline (항상 3점) | 0.0000 | 1.2199 |
| 현행 어휘 폴백 | 0.2704 | **1.6610** |
| 이 모델 | 0.7775 | 0.4407 |

**폴백이 상수보다 MAE가 나쁘다.** 어휘 가산이 실질적으로 아무 일도 하지 않는다. 데이터셋의 24.2%가 이 방식으로 라벨링돼 있다.

### 2. 그런데 모델이 그 자리를 대신할 수도 없다 (확인됨)

한 소스로 학습해 다른 소스를 예측하는 leave-one-source-out 전이:

| 평가 대상 | QWK |
|---|---|
| → jobkorea (9,933행) | 0.0603 |
| → saramin (20,463행) | 0.0372 |

**사실상 무작위다.** 소스 하나만 바뀌어도 무너진다면, 모델이 배운 것은 "채용 긴급성"이 아니라 **"그 소스의 정규식 규칙"** 이다. jobkorea는 `남은기간 N일`, saramin은 `접수기간` 창 길이로 라벨이 만들어지니, 규칙이 다르면 배운 것이 통하지 않는다.

따라서 measurable 모델을 unmeasurable에 적용하는 것은 **근거가 없다.** 실제로 적용해보면 예측이 1점에 79.8% 쏠리는데, 이는 학습 분포를 그대로 투사한 label shift이지 그 공고들이 덜 급하다는 증거가 아니다.

### 근본 원인

문제는 모델도 전처리도 아니고 **라벨**이다. 소스마다 다른 규칙으로 만든 라벨은 소스별로 다른 타깃이며, 어떤 모델도 이것을 하나의 개념으로 학습할 수 없다.

이 데이터셋으로 "본문을 읽고 채용 긴급성을 일반화하는" 모델을 만들려면 **사람이 붙인 소량 정답 세트(300~500건)** 가 필요하다. 지금 측정할 수 있는 것은 "규칙을 얼마나 잘 복제하는가"뿐이고, 규칙 자체가 맞는지는 확인할 방법이 없다.

## v3 — 라벨을 고치고 다시 잰 것

위의 "근본 원인"이 라벨이라고 지목했으니, 라벨을 고치고 그 진단이 맞았는지 확인했다.
규칙은 [`../urgency_rule.py`](../urgency_rule.py), 학습은 `train_urgency_v3.py`.

### 무엇을 고쳤나

| | 내용 | 실측 |
|---|---|---|
| 수정 1 | jobkorea가 모집인원을 `○○`로 가려서, 옆의 **지원자 수**가 모집인원으로 읽히던 버그 | 4,165행에서 발생. measurable의 11.4%가 등급 오류 (`4→2점` 1,487건) |
| 수정 2 | 마감 신호를 **접수 창 길이**(마감일−시작일)로 소스 통합. jobkorea가 쓰던 `남은기간`은 크롤링 시점에 의존하는 값이라 폐기 | 라벨 5,694행(14.1%) 변경 |

`남은기간`이 문제였던 이유가 핵심이다. 그건 공고의 속성이 아니라 **내가 언제 봤는가**의
속성이다. 하루 뒤에 크롤링하면 라벨이 달라진다. 반면 접수 창 길이는 두 소스에서
같은 분포로 뽑힌다(둘 다 p50=30일).

**소스 간 라벨 정합성** (measurable 30,569행, 상위 등급 4+5점 비율)

| | jobkorea | saramin | 격차 |
|---|---|---|---|
| v2 | 45.2% | 2.0% | **22.9배** |
| v3 | 5.4% | 2.0% | **2.7배** |

같은 개념이라면 나올 수 없는 격차였다.

### 진단이 맞았나 — cross-source 전이

같은 행 · 같은 split · 같은 모델(LinearSVC) · 같은 텍스트 조건에서 **라벨만** 바꿔 비교했다.
v2 라벨 재현치가 이 문서 위쪽 표(0.0603 / 0.0372)와 소수점 셋째 자리까지 일치하므로,
차이는 라벨 변경만의 효과다.

| 평가 대상 | v2 라벨 | v3 라벨 | 변화 |
|---|---|---|---|
| → jobkorea (9,933행) | 0.0600 | **0.2035** | +0.1435 |
| → saramin (20,635행) | 0.0373 | **0.0582** | +0.0210 |
| 평균 | 0.0486 | **0.1309** | +0.0822 |

**QWK가 2.7배 올랐다. 진단은 맞았다.**

### 그런데 전이는 여전히 쓸 수 없다

여기서 멈추면 과장이 된다. QWK만 보고 "좋아졌다"고 하면 안 되는 이유가 있다 —
**QWK도 MAE도 라벨 분포에 의존**하는데 v2와 v3은 분포가 다르다. 그래서 각 라벨
세트에 **자기 상수 베이스라인**(train 라벨 중앙값)을 깔고 그 대비로 다시 쟀다
(`compare_v2_v3.py`).

| 라벨 | 상수 대비 MAE 개선 | QWK |
|---|---|---|
| v2 | +16.6% | 0.0529 |
| v3 | **−30.1%** | 0.1307 |

**v3 전이 모델은 "항상 2점 찍기"보다 MAE가 나쁘다.**
`class_weight='balanced'` 탓인가 싶어 가중치 없는 모델도 같이 돌렸는데 −26.3%로 같았다.

모순처럼 보이지만 아니다. 모델은 **순서 정보(ranking)는 배웠지만 점 예측(calibration)이
나쁘다.** QWK는 순서를 보상하고, MAE는 한 클래스(2점 50%)에 몰린 분포에서 예측을
퍼뜨리는 것을 벌한다.

정리하면 라벨 수정은 전이를 **"사실상 무작위"(QWK 0.05)에서 "약한 신호는 있음"(QWK 0.13)**
으로 옮겼다. **"쓸 수 있음"으로는 옮기지 못했다.** 학습에 없던 사이트에 이 모델을
쓰지 말라는 결론은 v2와 같다.

### 최종 모델 (in-domain)

| 항목 | 값 |
|---|---|
| 알고리즘 | XGBoost (`multi:softmax`, early stop @ 301/400) |
| 피처 | TF-IDF 1~2gram, 30,000 |
| 텍스트 조건 | `masked+clean` |
| 학습 | measurable 19,494 / val 4,849 / test 6,050 |
| 예측 | 클래스 확률의 기댓값 반올림 |
| 파일 | `models_v3/urgency_model.joblib` |

**test 성능** (measurable hold-out 6,050행, 최종 1회 평가)

| | 상수 베이스라인(2점) | v3 모델 |
|---|---|---|
| MAE | 0.5345 | **0.3474** (−35.0%) |
| QWK | 0.0000 | **0.6124** |
| ±1점 이내 | 96.94% | **98.02%** |
| Macro F1 | — | 0.5328 |
| Accuracy | — | 0.6736 |

> ⚠️ **v2의 in-domain 숫자(QWK 0.7874)와 직접 비교하지 말 것.** 라벨이 다른
> 타깃이라 난이도 자체가 다르다. v2가 높았던 것은 jobkorea 라벨이 4·5점에 45%
> 퍼져 있어(= 크롤링 시점이 섞여 있어) 분리하기 쉬웠던 탓이 크다.
> 비교가 가능한 것은 위의 전이 실험처럼 **다른 조건을 모두 고정했을 때**뿐이다.

### v3에서 고친 실험 설계

- **모델 선택을 validation으로.** `train_urgency_transfer.py`는 EXP-A의 모델을
  test QWK로 골랐다(test contamination). v3은 validation으로 고르고 test는 마지막
  한 번만 본다. 예측 방식(argmax vs 기댓값)도 validation에서 정한다.
- **상수 베이스라인을 MAE 최소 상수로.** v2는 "항상 3점"과 비교했는데, 그건 MAE를
  최소화하는 상수가 아니라 모델에 유리한 기준이었다. v3은 train 중앙값을 쓴다.

### v3에서 못 고친 것

- **어휘 폴백은 그대로 두었다.** v3 라벨 위에서 다시 재도 상수보다 MAE가 나쁘다
  (2.0093 vs 1.1924). 대체할 검증된 방법이 없어서 남겼다.
- **`채용 시 마감`이 두 신호에 중복 계상된다.** rolling(+10)과 조기마감(+12)에
  모두 걸려 한 문구로 22점이다. v2도 saramin에서 그랬고, 가중치를 손대면 위의
  v2 대비 비교가 오염되므로 이번 라운드에서는 두었다.

- `models_baseline/` — 통제 조건 4종 비교용. 전체 데이터 학습
- `models/` — v1 (참고용, 거품 포함)

**추론**
- `predict_urgency.py` — **최종 추론 인터페이스**. 전처리 + 기댓값 예측 + 범위 플래그

**학습·분석 스크립트**
- `train_urgency_model.py` — v1
- `train_urgency_baseline.py` — 통제 조건 그리드 (`full`/`masked`/`clean`/`masked+clean`) + 베이스라인 사다리
- `train_urgency_transfer.py` — v2 최종 설계. EXP-A(in-domain) / B(전이) / C(폴백 대체) / D(적용)
- `train_urgency_v3.py` — **v3 학습**. 같은 행·같은 split에서 라벨만 v2/v3로 바꿔 전이 비교
- `compare_v2_v3.py` — 상수 베이스라인 대비로 v2/v3 전이를 다시 재기 (분포 차이 상쇄)
- `finalize_model.py` — argmax vs 기댓값 예측 비교, 최종 확정
- `boilerplate.py` — 사이트 템플릿 제거
- `check_label_leakage.py` — 라벨 누출 진단
- `check_source_boilerplate.py` — 템플릿 제거 검증 (source 분류 정확도로 측정)

**로그**: `full_run_baseline.log`, `full_run_clean.log`, `full_run_transfer.log`, `full_run_v3.log`

## 재현

```bash
# v3 (현재)
python ../urgency_rule.py --write   # 라벨 재생성
python train_urgency_v3.py          # 학습 + v2 대비 전이 비교 (약 11분)
python compare_v2_v3.py             # 상수 대비 재측정 (약 1분)

# v2 (보존용 재현)
python train_urgency_baseline.py --skip-xgb    # 통제 조건 비교 (수 초)
python train_urgency_transfer.py               # v2 최종 설계 (약 14분)
python finalize_model.py                       # 예측 방식 확정
python predict_urgency.py                      # v2 자기검증
```

분할·시드가 결정론적이라 동일 결과가 재현된다. `predict_urgency.py`의 자기검증이
저장된 최종 지표 5종(QWK / MAE / ±1점 이내 / Macro F1 / Accuracy)과 소수점까지
일치하는지 매번 확인한다.

## 알려진 제약

- 학습·평가 모두 데이터 스냅샷 기준이다(v3은 `master_merged_v3.json`). 공고가
  갱신되면 재학습이 필요하다.
- 라벨 버전이 다른 모델의 in-domain 지표는 서로 비교할 수 없다. 비교하려면
  `compare_v2_v3.py`처럼 다른 조건을 고정하고 상수 베이스라인 대비로 봐야 한다.
- 단일 hold-out으로 측정했다. 교차검증 기반 신뢰구간은 없다.
- 보조 피처(리스트 컬럼 개수·본문 길이)는 제외했다. v1이 그 채택 여부를 test로
  결정해 test contamination이 있었고, validation 기반 재선택은 하지 않았다.
- 한국어 형태소 분석을 쓰지 않았다. 어절 단위 토큰이라 `학력은`/`학력이`가 별개
  피처가 된다. Kiwi·Mecab 도입 시 어휘 크기와 성능 모두 개선 여지가 있다.
