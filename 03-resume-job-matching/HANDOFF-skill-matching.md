## ⚠️ 브리프에서 **바뀐 것 네 가지**

### 1. 브리프의 하한선(Recall@10 92.5%)은 쓰지 마세요

그 숫자를 재현하는 스크립트가 저장소에 없었고, 지금 조건에서는 재현되지
않습니다. 조건이 달라졌기 때문입니다 — 후보 풀 크기가 다르고, 기술명을
표준화하면서 어휘가 11,887종 → 158종으로 줄었습니다.

**새 기준선**(`python eval_proxy.py --self-test`, 질의 200건, 풀 23,852건):

| 방식 | Recall@10 (100% / 60% / 40% 보유) | MRR |
|---|---|---|
| 단순 IDF 합산 | 68.0% · 39.0% · 23.5% | 0.464 · 0.273 · 0.140 |
| **+ 길이 정규화(`/√Σidf`)** | **95.0% · 57.0% · 28.0%** | 0.837 · 0.388 · 0.120 |
| 무작위 | 0.00% | 0.000 |

**이 표의 아래 줄을 넘기는 게 목표가 아닙니다.** 튜닝하다가 점수가 내려가면
뭔가 깨진 것이다 — 그 용도입니다.

### 2. 점수를 **단순 합산으로 두지 마세요** — 이게 이번 라운드의 핵심입니다

브리프는 "IDF 가중 합산"까지만 적었는데, 실제로 돌려보니 그것만으로는
**동점이 대량 발생합니다.** 질의 200건 실측(요구 스킬 100% 보유 = 가장 쉬운 조건):

```
정답보다 점수가 높은 공고    중앙 0건    ← 순위 자체는 정확하다
정답과 점수가 똑같은 공고    중앙 5건 · 평균 94건
그중 동점이 11건 이상인 질의  200건 중 88건 (44%)
```

즉 **모델이 못 맞히는 게 아니라, 똑같은 점수의 공고 수십~수백 개 사이에서
정답이 몇 번째로 나오느냐가 운에 달려 있습니다.** 어휘가 158종인데 공고가
23,852건이라 스킬 집합이 겹치는 공고가 많아서 생기는 구조적 현상입니다.

그래서 **타이브레이크·정규화가 이 작업의 실질적인 설계 결정**입니다. 위 표에서
`/√Σidf` 하나만 넣어도 68.0% → 95.0%입니다. 어떤 정규화를 쓸지(자카드 · 코사인 ·
공고 스킬 수로 나누기 · 제목 일치 가산…)를 프록시로 비교해 고르시면 됩니다.

### 3. 설계 결정 세 가지는 **플래그로** 두세요 (브리프와 동일, 확정됐습니다)

상위 개념 함의 · 스킬 0개 이력서 · `compute_related_techs` — 회의에서 고르지 않고
**양쪽 다 만들어 프록시로 재기로** 했습니다. 기본값만 정해서 먼저 만드시고,
비교는 제가 돌리겠습니다. 여기에 하나 추가됐습니다 — **`skills_extra` 사용 여부**
(제가 재봤을 땐 65.7% vs 68.7%로 **오히려 조금 나빴습니다**. 참고만 하세요).

### 4. 스킬 필드는 `job_pool`이 이미 합쳐서 줍니다

브리프의 `final_techs + hard_skills`(79.1%)는 그대로 유효하고, 거기에 본문에서
직접 뽑은 것까지 합쳐 놨습니다. 실측 커버리지:

```
final_techs 만          46.6%      ← 이것만 쓰면 절반이 매칭 불가
∪ hard_skills           79.1%
∪ 본문 추출             93.4%      ← job_pool 이 주는 것
```

그리고 표기를 표준화했습니다. 원본은 `JAVA` 248건과 `Java` 967건이 **따로**
세어지고 있었습니다(`Javascript`/`JavaScript`, `RESTful API`/`REST API`,
`Spring Framework`/`Spring`도 동일). 이력서에 "Java"라고 쓰면 `JAVA`만 적힌
공고와 안 맞던 상태였습니다.

## 채점하는 법

```python
from eval_proxy import evaluate
from skill_matcher import recommend

evaluate(recommend)          # 표를 출력하고 dict 를 돌려줍니다
```

공고의 요구 스킬로 **가짜 이력서**를 만들어, 그 공고가 상위에 회수되는지 봅니다.
정답 라벨 없이 숫자가 나옵니다.

> ⚠️ **이 숫자가 높다고 좋은 추천이라는 뜻은 아닙니다.** 가짜 이력서는 공고
> 스킬을 그대로 베낀 것이라 진짜 이력서보다 훨씬 쉽습니다. **"망가졌다"를
> 잡아낼 뿐 "좋다"를 증명하지 못합니다.** 02에서 Macro F1 0.8595 중 0.1975가
> 평가 설계의 거품이었던 것과 같은 자리입니다.

## 알아두실 것 — 데이터의 현재 상태

**추천 풀이 계속 커지고 있습니다.** 사람인 25,950건에 `title`·`company`·
`location`·`experience_level`이 전부 비어 있어서(수집 단계 누락) 추천 대상에서
빠져 있었는데, 지금 메타데이터를 다시 받아오는 중입니다(`backfill_saramin.py`).

```
백필 전     14,398건  (jobkorea + wanted)
현재        23,852건  (사람인 일부 반영, 계속 증가)
완료 후     약 40,000건
```

**코드는 안 고치셔도 됩니다** — `job_pool`이 백필 파일이 있으면 자동으로 씁니다.
다만 **풀이 커지면 Recall이 내려갑니다**(후보가 늘어나므로). 점수를 비교하실 땐
`python job_pool.py --report`로 그때의 풀 크기를 함께 적어 주세요.

**오늘 날짜로는 추천이 성립하지 않습니다.** 데이터가 2026.06~07 수집분이라
명시된 마감일이 남은 공고가 40,348건 중 **2건**입니다. 그래서 `as_of`를 과거로
두고 개발합니다(`as_of='2026-06-20'` → 지원 가능 15,500건). 이건 코드 문제가
아니라 입력 문제이고, 문서에 그대로 적을 예정입니다.
