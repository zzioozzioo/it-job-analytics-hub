## 2. 제 쪽 버그 ① — 채점 도구의 분모가 엉뚱한 공고 것이었습니다

`eval_proxy.idf_baseline()`이 공고별 분모를 **`job_id`를 키로 한 dict**에 담고
있었습니다. `job_id`는 이 데이터에서 **777종 1,554행이 중복**이라, 같은 키의
두 번째 행이 첫 번째의 분모를 덮어씁니다. 그러면 어떤 공고가 *다른 공고의*
분모로 나눠집니다.

`score = Σidf(hit) / √Σidf(job)` 인데 `job_techs ⊇ hit` 이므로 언제나
`Σidf(job) ≥ Σidf(hit)`, 따라서 **상한은 `√Σidf(hit)`** 입니다. 덮어쓰기가
일어나면 이 상한을 넘는 점수가 나옵니다. 실제 사례(`job_id=49146921` 질의):

| 같은 id의 행 | 요구 기술 | Σidf | √Σ |
|---|---|---|---|
| jobkorea 1행 | 2종 | 3.0344 | 1.7419 |
| jobkorea 2행 | 1종 | 0.7524 | **0.8674** ← 이 분모가 남음 |

`3.0344 / 0.8674 = 3.4981`. 이론 상한이 `2.1930`인데 이 값이 1위에 앉아
정답을 top-10 밖으로 밀어냈습니다.

**영향 실측**

| | 수정 전 | 수정 후 |
|---|---|---|
| 분모가 오염되는 `job_id` | 175종 | — |
| 질의 200건 중 top-10에 상한 위반 공고가 낀 질의 | **56건 (28%)** | **0건** |

`make_queries()`는 `~dup`으로 질의 쪽 중복을 막아뒀는데 채점 대상 쪽에는 그
방어가 없었습니다. 저장소 함정 목록의 **"(source, job_id) dict 조인 금지"** 를
제가 같은 파일에서 다시 밟은 것입니다. 분모를 dict가 아니라 **행 순서와
1:1인 리스트**로 바꿔 고쳤습니다.

## 3. 새 기준선 — HANDOFF의 표를 이걸로 교체해 주세요

질의 200건 · 풀 39,668건 · `seed=0` · `as_of=2026-06-20`.

| 방식 | 명령 | Recall@10 (100/60/40%) | MRR |
|---|---|---|---|
| 단순 IDF | `--self-test` | 65.0 · 39.5 · 25.0% | 0.461 · 0.253 · 0.158 |
| `/√Σidf` | `--self-test --norm` | **94.0** · 60.5 · 25.5% | **0.837** · 0.406 · 0.151 |

> ⚠️ **`92.5% / MRR 0.728`은 버그가 섞인 값입니다.** 2026-09-17 HANDOFF 갱신판이
> 이 값을 하한선으로 제시했고, `skill_matcher.py` 상단 docstring에도 인용돼
> 있습니다. 둘 다 위 표로 바꿔 주세요.

**그리고 제가 앞서 "재현 안 된다"고 폐기 선언했던 `94.0% / MRR 0.837`은
사실 맞는 값이었습니다.** 9/17에 제가 버그를 넣으면서 92.5%로 떨어진 것이었고,
고치니 셋째 자리까지 정확히 돌아왔습니다. 폐기 선언을 철회합니다.
(단순 IDF의 `66.0% / 0.468`은 여전히 재현되지 않습니다 — 이쪽은 dict 분모를
쓰지 않아 버그와 무관하고, 풀 크기가 달랐던 판으로 보입니다.)

### `skill_matcher`와 기준선의 관계

| | Recall@10 (100%) | MRR |
|---|---|---|
| 기준선 `/√Σidf` | 94.0% | 0.837 |
| `skill_matcher` (`length_norm`) | 94.5% | 0.830 |

**같은 수식이니 같게 나오는 것이 정상이고, 실제로 그렇습니다.** 남은 차이는
요인 분해로 확인했습니다 — Recall `+0.5%p`는 심지우님이 넣으신 **`job_id` 중복
제거**가 top-10 자리를 벌어준 몫(정당한 개선), MRR `−0.007`은 **동점 2차 정렬
키를 `job_id` 문자열로 둔** 몫입니다. 동점이 질의당 평균 94건이라 2차 키는
성능이 아니라 재현성 장치입니다 — 지금 그대로 두시면 됩니다.

## 4. 6종 비교 — `length_norm`(sqrt) 유지가 맞습니다

`python eval_proxy.py --compare-norms` (수정 후 재측정, 276초)

| 정규화 | Recall@10 (100/60/40%) | MRR (100/60/40%) |
|---|---|---|
| none | 65.0 · 39.5 · 25.0% | 0.461 · 0.253 · 0.158 |
| **sqrt** | **94.0 · 60.5 · 25.5%** | **0.837 · 0.406 · 0.151** |
| linear | 2.5 · 0.5 · 1.0% | 0.005 · 0.003 · 0.001 |
| count | 10.0 · 2.5 · 2.0% | 0.039 · 0.006 · 0.003 |
| cosine | 94.0 · 53.5 · 26.0% | 0.833 · 0.355 · 0.130 |
| jaccard | 94.0 · 58.5 · 22.5% | 0.837 · 0.388 · 0.116 |

- 100% 조건은 **sqrt·cosine·jaccard가 94.0%로 동률**입니다. 여기만 보면 못 고릅니다.
- 가르는 건 **60%·40% 조건**입니다. sqrt가 60%에서 60.5%로 가장 높고, MRR은
  40% 조건까지 포함해 전 구간 최고 또는 동률입니다.
- `linear`·`count`는 과도한 정규화로 무너집니다(2.5% · 10.0%). 요구 스킬이 적은
  공고가 전부 위로 올라와 버립니다.
- **따라서 `DEFAULT_SCORE_MODE = "length_norm"` 그대로 두시면 됩니다.**

> 정직하게 남겨둘 것: 버그가 있던 시절의 6종 표는 **기록이 없어 대조하지
> 못합니다.** 코드만 커밋됐고 결과 표를 문서에 남기지 않았습니다. 결론(sqrt)은
> 바뀌지 않았지만, 그때 표를 적어뒀다면 이번에 "무엇이 얼마나 달라졌나"를
> 말할 수 있었을 것입니다.

## 5. 제 쪽 버그 ② — pandas 백필 신고, 고쳤습니다

`BUG-saramin-backfill-pandas3.md` 받았습니다. **원인 분석은 정확합니다** — 다만
지목하신 지점보다 한 겹 아래가 범인이었습니다.

```python
def _blank(v):                      # 수정 전
    return v is None or (isinstance(v, str) and v.strip() in ('', 'None', 'nan'))
```

**문자열 `'nan'`은 있고 float `NaN`은 없습니다.** 그래서
`_blank(float('nan')) == False`가 되고, 지적하신 `값 or 백필값` 폴백이
`NaN`(truthy)에서 멈춥니다. 예상하신 장소에서 예상하신 이유로 틀려 있었습니다.

**고친 것 4곳** (`job_pool.py`)

| | 무엇 |
|---|---|
| 1 | `_blank()`가 float `NaN`을 잡는다 (`v != v`). 근본 원인 |
| 2 | **`_val()` 신설** — `load_pool()`의 `or` 폴백 4개를 전부 이걸 거치게 했습니다. pandas가 결측을 어떤 모양으로 주든 그 뒤로는 `None` 하나입니다 |
| 3 | `load_corpus()` 정리에 `.astype(object)` 추가 |
| 4 | **백필 부재 경고 · 병합 0건 경고** 신설 |

제안하신 `.where(~mask, None)`은 쓰지 않았습니다 — 그것도 pandas가 다시 `NaN`으로
승격시키면 같은 자리로 돌아옵니다. **소비 지점 방어가 버전에 무관하게 안전합니다.**

**검증 5가지** — 이 환경(pandas 2.3.3)에서는 원래 재현이 안 되어, 상황을 직접
만들어 재어 봤습니다.

| 경우 | 풀 크기 |
|---|---|
| 정상 경로 (회귀) | 39,668건 ✓ |
| 메타 결측을 `NaN`으로 주입 — **수정 후** | **39,668건** ✓ |
| 메타 결측을 `NaN`으로 주입 — **수정 전 `_blank`로 되돌림** | **14,398건** ← 신고 증상 정확히 재현 |
| 백필 파일 부재 | 14,398건 + 경고 ✓ |
| `test_job_pool.py` | 9/9 pass ✓ |

`or` 폴백을 저장소 전체에서 훑었습니다. 조용히 틀릴 수 있던 것은 방금 고친
4개가 전부입니다(`raw_text`의 `or ''`는 결측 0건이고, `NaN`이면 `TypeError`로
시끄럽게 죽으니 조용한 실패는 아닙니다).

### 그런데 pandas 버전이 안 맞습니다 — 확인 부탁드립니다

리포트에 환경이 "pandas 3.0.5 (`conda itjob` 환경 실측)"이라 적혀 있는데,

- 제 `itjob` 환경은 **pandas 2.3.3** 입니다.
- **PyPI에 pandas 3.x가 아직 없습니다.** `pip index versions pandas`의 최상이
  2.3.3이고 3.0.5는 목록에 없습니다.

수정 자체는 버전과 무관하게 유효하니 그대로 가지만, **심지우님 환경의 풀이
14,398건이었던 진짜 이유가 pandas가 아닐 수 있습니다.** 가장 흔한 후보는 그냥
**백필 파일이 `data/`에 없는 것**이고, 이 경우 증상이 완전히 동일합니다
(풀 14,398, 예외 없음, 조용함). 그래서 경고를 둘로 나눠 넣었습니다.

```
⚠️  사람인 백필 파일이 없어 추천 풀에서 saramin 25,270건이 통째로 빠집니다.
    ...                                      ← 파일이 없을 때

⚠️  백필 파일은 읽혔는데(25,270건) 실제로 병합된 공고가 0건입니다.
    ...                                      ← 파일은 있는데 병합이 실패할 때
```

**어느 경고가 뜨는지 알려주시면 둘 중 어느 쪽인지 바로 가려집니다.**

## 7. `require_techs` — `True`로 부르셔도 됩니다 (점수 완전 불변 확인)

스킬 0개 11,909건은 점수가 0이라 top-10에 못 옵니다. 그래서 풀에서 빼도
결과가 같을 것으로 봤고, **실측으로 확인했습니다.**

질의 집합을 하나로 고정하고 두 풀에 같은 질의를 던진 결과(기준선 sqrt):

| | Recall@10 (100/60/40%) | MRR |
|---|---|---|
| `require_techs=False` (풀 39,668) | 94.0 · 60.5 · 25.5% | 0.837 · 0.406 · 0.151 |
| `require_techs=True` (풀 27,759) | 94.0 · 60.5 · 25.5% | 0.837 · 0.406 · 0.151 |
| 차이 | **+0.0 · +0.0 · +0.0%p** | **±0.000** |

**세 조건 모두 소수점까지 동일합니다.** 그래서 `skill_matcher`의 `_load()`에서
`require_techs=True`로 부르시면 풀이 30% 줄어듭니다. `iterrows()` 비용이 행 수에
비례하니 ④ 성능 작업과 함께 하면 이득이 곱해집니다.

데이터 계층의 기본값은 `False`로 남깁니다 — 4단계 임베딩이 들어오면 스킬 0개
공고가 텍스트로 매칭될 수 있어서, "스킬로 매칭한다"는 전제는 쓰는 쪽이 거는 게
맞다고 봤습니다.

### 이 과정에서 `eval_proxy`의 취약점을 하나 더 찾았습니다 (제가 고칩니다)

처음에는 `evaluate()`를 두 풀에 각각 돌려 `96.5%` vs `94.0%`를 얻었는데,
**그건 허상이었습니다.** `make_queries()`가 pool의 **행 인덱스**로
`rng.shuffle(idx)`·`random.Random(seed + i)`를 하기 때문에, 풀이 바뀌면 `seed`가
같아도 질의 집합과 남긴 스킬이 달라집니다. 정답 job_id 목록을 대조해 보니 실제로
달랐습니다.

→ **풀이 달라지는 실험에서는 질의를 넓은 풀에서 한 번 만들어 양쪽에 같이
던져야 합니다.** 위 표는 그렇게 다시 잰 값입니다.

**인터페이스를 고쳐뒀습니다** — `make_query_set()`을 추가하고 `evaluate()`가
`queries=`를 받습니다. 풀이 다른 둘을 비교할 때는 이렇게 쓰시면 됩니다.

```python
qs = ep.make_query_set(wide_pool, n=200, seed=0)      # 넓은 풀에서 한 번만
a = ep.evaluate(rec_a, pool=wide_pool,   queries=qs)
b = ep.evaluate(rec_b, pool=narrow_pool, queries=qs)  # 같은 질의를 던진다
```

단독 측정은 지금처럼 `queries` 없이 부르면 됩니다(동작 그대로입니다).
`queries`에 없는 보유율을 채점하려 하면 `ValueError`로 멈춥니다 — 조용히 다른
질의로 재는 것보다 낫다고 봤습니다.
